# ADR 0005: Direct Gmail API with External OAuth Bootstrap

- Status: Accepted (implementation offline-verified; authenticated live verification pending)
- Date: 2026-09-06
- Supersedes: [ADR 0002](0002-external-command-dependencies-and-cli-adapters.md)

## Context

The experimental Gmail connector delegates authentication and message reads to
`gws`. Its command contract and environment/keychain dependencies add failure
points; the current user-visible error does not identify the underlying Google
failure. Earlier local evidence recorded insufficient authentication scopes,
but that does not establish the cause of every later command failure.

The user requested a replacement that does not use `gws`, choosing the easiest
maintainable approach and producing design and implementation documents without
human approval checkpoints. Cybort now has an injectable HTTP client supporting
form posts, bounded responses, and monotonic deadlines. Gmail collection needs
only token refresh, one message-list request, and metadata retrieval.

## Decision

Replace the implementation behind `adapter = "gmail"` with direct Gmail REST
through the existing `HttpClient`, with no new gems or runtime executables.
Use `gcloud auth application-default login` with a user-owned Desktop OAuth
client and explicit Gmail read-only scope only during external setup. Use a
separate `CLOUDSDK_CONFIG` directory per mailbox. At runtime, read only the
explicit per-instance authorized-user credential file; do not use ambient ADC
discovery or execute an authentication command.

Cybort owns the bounded refresh-token exchange and in-memory access token. It
does not own browser login, token-file writes, keychain access, or revocation.
Failure messages identify a fixed operation/category/status and give static
guidance without retaining remote error bodies or credentials.

Preserve instance IDs, canonical message IDs, bounded first-page semantics,
normalization, cache planning, retention, and independent persistence. Gmail
does not opt into snapshot replacement. Missing runtime credentials fail only
the affected remote source and do not prevent a fresh cache read.

This ADR carries forward the generic hybrid-adapter decision from ADR 0002:
connectors may still declare executable dependencies when appropriate, with
context-aware preflight and injected bounded argument-vector execution. Retain
`CommandRunner`, `DependencyChecker`, and their tests. Their existence does not
justify retaining a command dependency for Gmail.

## Alternatives

The official `google-apis-gmail_v1` and `googleauth` libraries are maintained and
viable. They introduce another HTTP/auth configuration boundary for a small API
surface already served by Cybort's transport. Using only `googleauth` still
splits token and data transports. Reconsider these libraries if requirements
expand substantially beyond this bounded read flow.

Using `gcloud` for each fetch retains a subprocess dependency and does not
replace Gmail's data API. Owning a desktop OAuth callback server adds
authentication UX and credential-write responsibilities. IMAP changes mailbox
query/content/identity handling without eliminating authentication setup.

## Consequences

- Runtime Gmail collection has no CLI installation/version/keychain dependency.
- Users still need a Google Cloud project, enabled Gmail API, OAuth consent,
  and a credential file generated by external setup. Setup is not zero-effort.
- Cybort maintains a small refresh/REST boundary and safe error mapping instead
  of command invocation and output parsing.
- Google scope, verification, admin restrictions, and refresh-token expiry
  remain applicable. A fixture test cannot verify a live grant.
- Existing Gmail configurations need a credential file for the next remote
  fetch, while fresh caches remain usable. Migration preserves local identity
  when the account stays the same.
- The old ADR's `gws` version gate is retired for the replacement. The direct
  implementation is now present and offline-verified, but its authenticated
  smoke test remains the release gate; Gmail therefore remains experimental.
